# Auditoría durable local: contrato y evidencia

`durable_audit.SQLiteAudit` satisface `AuditSink.append` y `ReadAuditSink.append_read` con una conexión SQLite **local, dedicada y propiedad del caller**. No abre archivos al importar, no conoce configuración de producción ni se monta en el runtime. Canon unchanged: prueba de infraestructura local sin nueva persistencia de negocio, autoridad ni conexión productiva. El alcance acordado sigue siendo la instalación actual de SamChat Plataforma Sports y sus cuentas existentes, sin modificar la separación de las tres razones sociales.

La migración `initialize_local_audit(connection)` es explícita y separada del constructor. Requiere archivo persistente, ninguna base adjunta ni transacción pendiente, y rechaza tablas ajenas. Crea exclusivamente versión de esquema, tabla de recibos, índice por actor y triggers que impiden UPDATE/DELETE. Repetirla sobre su esquema compatible no borra recibos. No es código de inicialización del servidor ni autorización de migración productiva.

El caller abre/cierra su conexión y define timeout; debe mantener el journal durable y `synchronous=FULL` o `EXTRA`. La migración establece FULL; el adapter valida la configuración en cada operación y rechaza OFF/MEMORY. Conexiones nuevas deben cumplir el mismo contrato. Se recomienda una conexión por worker; la instancia serializa sus llamadas con un lock y nunca comparte una transacción con código de negocio.

`append(actor_id=..., action=..., outcome=...)` devuelve UUID opaco solo después de COMMIT. `append_read(actor_id=..., action=..., evidence_digest=..., scope_digest=...)` exige SHA-256 hexadecimales y registra READ_VERIFIED; no admite el resultado, payload ni contenido del scope. Acciones y outcomes pertenecen a vocabularios finitos del catálogo/MCP. El actor es un identificador opaco validado; no se permiten email, espacios ni objetos arbitrarios. El almacenamiento confía en que el caller suministra el actor ya autenticado, nunca un argumento del modelo.

Cada recibo contiene únicamente ID, actor, acción, outcome, hashes de evidencia/ámbito cuando corresponden, timestamp nanosegundos y hash canónico del registro. Eventos sin identidad pueden tener actor nulo, pero no son recuperables mediante la consulta por actor. `get_for_actor(receipt_id, actor_id=...)` consulta ambos identificadores mediante parámetros, devuelve None para actor ajeno y valida el hash antes de devolver el recibo inmutable. No es un endpoint de autenticación ni permite al usuario elegir otra identidad.

La escritura usa BEGIN IMMEDIATE, INSERT parametrizado y COMMIT: conexiones concurrentes serializan sus escrituras y cada evento obtiene un ID distinto. Si falla INSERT/COMMIT, se intenta ROLLBACK, no se devuelve recibo y se emite un error estable sin SQL, path o mensaje original. Si ya existe una transacción del caller, se rechaza sin commit/rollback ajeno. Un resultado ambiguo por caída del proceso después de COMMIT requiere verificación; este adapter **no** promete exactly-once, ni implementa idempotencia o atomización con mutaciones de negocio. Registrar varios intentos de lectura no significa duplicar capturas.

Los triggers y el SHA-256 detectan modificación accidental o cambios sin recomputar el digest. No son firma criptográfica, cadena externa ni protección contra un administrador del archivo capaz de quitar triggers/recalcular hashes. El hash de un reporte minimizado no anonimiza mágicamente datos de baja entropía; acceso al archivo y política de retención siguen bajo control del dueño de almacenamiento. No se registra contenido de menores, archivos, tokens, correos, teléfono ni errores privados. La duración de retención, permisos del archivo, backups, borrado autorizado, monitoreo y recuperación productivos requieren diseño/validación aparte.

Pruebas con fixtures: reapertura e igualdad del recibo, aislamiento entre actores, esquema mínimo, triggers de inmutabilidad, hash alterado, 24 escrituras concurrentes desde conexiones independientes, fallos de INSERT/COMMIT, bloqueo/readonly, transacción ajena preservada, rechazo de memoria/DB ajena/schema incompatible/journal no durable, y validación que evita texto arbitrario. Ninguna prueba conecta bases, usuarios o servicios reales. Esta evidencia demuestra persistencia local del recibo, no auditoría productiva ni habilitación del plugin.
